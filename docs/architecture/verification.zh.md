# 验证 —— 并行验证器，以及那条回到执行的 loop

这里的验证不是结尾产出的一份报告。它是一条**带返回边的 loop**：失败不会让流水线
停下，失败会**产生工作**。

有两点让它值得单独一页 —— 验证器是并发跑的，以及它对失败的处理方式，就是这个系统
的整体形状。

## 一个验证点是什么

验证读 PRD、架构文档和测试设计，把它们变成一份由**验证点**组成的计划。每个点有
id、方法、优先级和预期结果，并且每个点都是对着**运行中的代码**检查，而不是对着
执行器的总结。

| 方法 | 怎么检查 |
|---|---|
| `automated_test` | 一条命令，由退出码判定 |
| `code_review` | 对相关代码做一次 LLM 审查 |
| `ui_validation` | 真实浏览器驱动 UI |
| `api_test` | 一次 HTTP 请求，对响应做断言 |
| `manual_check` | 需要人 —— 报告出来，而不是静默通过 |

## 它并行运行，上限来自舰队

验证点按**方法**分组。组与组并发，组内的验证点也并发。

两层都有上限，而且两层用的是**同一个数**：验证场景的 provider 此刻能同时服务多少个
验证点。

!!! note "宽度来自 provider，而不是手写的一个数"
    这个宽度是该场景自己那条链上各 provider 的和：每个 provider 声明的 cap，按它
    5 小时窗口还剩多少缩放 —— 也就是执行侧为自己的池子本来就在算的那套
    （`dynamic_provider_concurrency.fleet_capacity`），读的是**同一份**配额载荷，
    和派发路径拿到的是同一份。一个 provider 声明 10 就是 10；两个就是 20；
    某个只剩 40% 窗口就是 4；某个窗口**已关闭就失去它的份额**，整条链都关时答案是
    `0` —— 不会往一个关着的窗口里派活。

    它在**每次 gate 要放行的时候重新读**，不是轮次开始时定死。轮次跑到一半关掉的
    窗口会缩小舰队，而一个在构造时就把宽度定死的 gate 看不见这件事。

`parallelism_cap`（仍在 `verification.yaml` 里，仍是 `4`）是**兜底**：只有在
推不出任何东西的时候才生效 —— 也就是验证场景的链根本解析不出来。它刻意**不是**
"什么都没有就跑 4 个"的规则；一个测出来的 `0` 是配额给的真答案，就按真答案用。

组之上还有第二层 plan-wide 上限，防止各组的扇出相乘后超过 provider 实际有的槽位。
场景能解析时，它读的是和各组**同一个实时数字**；链解析不出来时，才退回到声明容量
天花板（`provider_capacity.configured_capacity_ceiling`）。

每个组用一对 `group_started` / `group_completed` 事件把自己那一段在 JSONL 日志上
括起来，带上方法、点数以及该组的通过/失败计数 —— 所以进度在轮次**运行中**就能读，
而不是只能等到最后。

## 等一个关着的配额窗口

当场景没有可派发的 provider，原因是**配额窗口关了**（不是链解析不出来，也不是本地池
满了）时，派发不会失败。它会把调用方的工作时钟挂起（所以等待不会被记到那个本来用来
抓"卡死调用"的预算上），记一条日志说明正在等、哪些 provider 关着、最早什么时候有
任何一个回来，然后按固定五分钟的节拍探测配额载荷，**要探多久没有上限**。窗口关多久
是 provider 的事实；调用方按自己编的时限放弃，换不回窗口，只会给自己判定的"已经结束
的等待"记一个失败。

**整个进程只有一个** watchdog，不是每个等待中的派发一个。这份载荷一次请求会扇出到
每个 provider，所以每个等待者一个 watchdog，等于每个等待者每个周期花一次请求去学同一
件事。同时发起的询问会被合并：一个调用者去读，其余的等它并取它的答案。在八个验证点
睡在同一个关闭窗口上的实测里：**改之前每个 tick 8 次请求，改之后 1 次**。

等待不是卡死。睡在关闭窗口上的验证点没有子进程、没有 stdout、没有进度可报，所以
sub-agent watchdog 的过期扫描会跳过它 —— 否则一次长到越过阈值的等待，会把 kill 路径
花在一个并不存在的进程上，然后把 handle 扔掉，等窗口重开、真正的子进程起来时，watchdog
已经被自己解除了武装。

## 一轮失败之后会发生什么

这就是那条返回边：

```
   ┌───────────────────────────────────────────────────────┐
   │                                                       │
   ▼                                                       │
[Execution] ──► [Verification round N] ──► PASSED ──► done │
                        │                                  │
                        └── FAILED ────────────────────────┘
                             │
                             ├─ requirement deviations + failed points
                             ├─ turned into repair tasks
                             └─ written into state.db  ──► back to Execution
```

关键的细节是**修复任务去了哪里**。它们被直接写进状态数据库（`state.db`，经由
`PlanTaskRepository`），执行器下一次加载时把它们从那里对账进 DAG —— 于是它像捡起
任何其他任务一样捡起它们：

- 同样的并发规则（依赖层、冲突图、provider 槽位、文件锁）；
- 同样的双信号完成判定；
- 同样的 git 检查点。

修复没有第二条更弱的执行路径。**修复任务就是任务。**

这个去向是刻意的，所以值得说明它排除了什么：**执行状态活在数据库里，不在产物文件
里。** 计划目录下的 JSON 是*种子*和*记录* —— `tasks.json` 是任务生成产出的那张图，
没有任何东西会重写它来携带运行结果。于是一轮修复不会留下第二份任务图让后来的读者
去和第一份对账，也不会留下一个写了一半的文件在进程中途死掉时丢掉。

breakdown 追加的子任务走同一条路，理由也相同：refiner 也把它们写进数据库，所以
一次中途拆分是一行记录，而不是那张图的第二个版本。两者是同一个机制 —— *新工作出现
在 `state.db` 里，执行器下次加载时把它对账进 DAG* —— 把它收敛成一个机制，才让崩掉的
一轮是可恢复的，而不是有歧义的。

修复生成也是**自动**的 —— "验证失败"和"执行器开始修"之间没有人工确认门槛。如果
修复生成本身失败了（provider 抖动、空回复），那会被记下来并在下一轮重试，而不是把
计划停下来等人。

## 主题外 VP 删除豁免

验证点清单默认是**只标记不删**的：废弃一个验证点是给它盖一个"已废弃"的标记，审计
痕迹留着，这条判据本身还在计划里。

有一条例外：**主题外**的验证点可以被真正移除 —— 与本次计划主题无关的那一条。之所以
要开这条豁免，是因为判定本身必须有一条出口：一条跑题的验证点每轮都被完整跑一遍，
验证成本随轮次增长，而它证明的从来不是这次计划的事。

豁免只有一种成立方式，三个限定词缺一不可：

| 限定词 | 含义 | 缺了会怎样 |
|---|---|---|
| `llm_irrelevant` | 相关性判定明确判它无关（判定不可用时按"相关"兜底，不构成移除理由） | 兜底也会移除，判定一失效就误伤计划 |
| 审计已落盘 | 移除记录已经追加写进移除审计文件 | 移除没有证据，"归档过了"只是一句可以被抹掉的声明 |
| 主题外 | 范围只限与计划主题无关的验证点 | 改判据、改断言也落进这条豁免，严格度静悄悄地流失 |

顺序是承重的：**先归档、后移除**。审计写不进去（磁盘满、只读、路径不可写）时，那条
验证点**留在计划里** —— 一次没有审计的移除是一次静悄悄的严格度损失。

三个限定词之外的一切情形，废弃仍然只是标记。这条豁免是**追加**在既有规则（"绝不
修改已有验证点"、"废弃只标记不删除"）之上的，不是对它们的改写。

## 循环有四个方向的边界

| 停止条件 | 含义 |
|---|---|
| `passed` | 验收标准成立，结束。 |
| `max_rounds_reached` | 轮次预算耗尽。 |
| `same_failure_repeated` | 连续两轮失败的**验证点集合完全相同**。 |
| `user_stopped` | 操作者主动停止。 |

`same_failure_repeated` 是值得理解的那一个。如果第 N 轮和第 N+1 轮在完全相同的点上
失败，说明**修复没在起作用**。继续下去只会烧掉剩下的预算、走到同一个地方，所以循环
提前停下并说明原因。

!!! warning "这个判据按 status 判，不按 reason 字符串判"
    自动循环识别"收敛"的方式是编排器返回 `status == "loop_stopped"` —— **不是**
    比较 `stop_reason` 字符串。早期版本比的是字符串，而字符串改名之后那个守卫就静默
    不再匹配：那段时间里收敛判据从未生效，每一轮都烧完整个预算，最终记录下来的
    reason 还被 `max_rounds_reached` 覆盖掉了。如果你要动这条契约的任何一侧，
    两侧一起动。

## 怎么读一个停下来的循环

以 `loop_stopped` 结束的计划和失败的计划**不是一回事**。它意味着系统已经**无路可进**
—— 要么预算用尽，要么触发了同一失败集合的判据 —— 于是停下而不是空转。`stop_reason`
在 `GET /api/verification/{plan_id}/status` 的响应里，`plans/{plan_id}/logs/` 下的
逐轮日志会说清每一轮是哪些点在失败。见[运行它](../operations/running.md)。

不是每一个"仍在运行"都真的在运行：一轮验证如果长时间没有任何日志输出，它卡住的
可能性远大于它慢，这正是 watchdog 心跳存在的意义。见
[设计说明](../development/design-notes.md)。

## 重启一个停下来的循环

`POST /api/verification/{plan_id}/reset` 会把轮次计数器归零、清掉本轮产物，
**但不动验证点清单**，然后 `/start` 再跑一次。如果你还希望下一轮重新生成验证点，
传 `{"clear_verification_plan": true}` —— 那被刻意做成第二步，因为重新生成计划会
改变"通过"的定义。

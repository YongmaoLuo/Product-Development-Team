# 执行 —— 并发地跑任务

任务不是一个个串行跑的。有意思的问题不是"它们**能不能**一起跑"，而是**什么时候
不可以** —— 这一页讲的就是这个问题在三个不同的层上分别怎么回答。

## 第一层 —— 依赖图决定什么**可以**一起跑

`tasks.json` 是一张图，不是一个列表。每个任务声明它依赖什么，执行器把这些边变成
**依赖层**：同一层里的东西可以同时开始，下一层要等上一层做完。

这是粗粒度的答案，也是**动手之前你就能评审**的那个 —— 它就在任务图里。

## 第二层 —— 冲突图决定什么**实际**一起跑

一个依赖层并不自动安全。两个任务可以互相没有声明依赖，却都在改同一个文件。

所以在一层内部，执行器按每个任务声明的 `files_to_modify` 建一张**冲突图**，把这一层
切成互不共享文件的 *micro layer*：

- 共享文件的任务落进同一个连通分量，跨 micro layer **串行**；
- 不共享文件的任务合并成一个 micro layer，**并行**。

声明 `__UNKNOWN_MODIFICATIONS__` 的任务意思是"我没说我会碰哪些文件"，**不是**
"我什么都碰"。这类任务拿到一个私有的冲突键，于是它们**彼此之间**串行，但不与那些
声明了文件的任务串行。（它们曾经共享同一个哨兵键，结果把每个未知任务都塌进同一个
分量，让那类计划的并行度归零。这就是哨兵要被特殊处理的原因。）

## 第三层 —— 计划落空时靠什么兜

前两层都是**前向计划**：它们的质量只取决于任务声明了什么。一个任务完全可能碰到它
没声明的文件，而那时图对真实的冲突是沉默的。

三个机制填这个缺口：

**provider 槽位。** 另有一个按 provider 计的预算，限制同时在飞的子 agent 数量。
上限在派发时从实时的 provider 容量表解析，所以一个慢的或被限流的 provider 会自己
把它那一份节流，而不是等到撞墙才发现。

**运行时文件锁。** 任务动它的目标文件之前，执行器为这些文件拿真实的 OS 级文件锁，
任务结束时释放。这跑在任务本身的同一条路径上，所以锁覆盖的是整段
*读 → 改 → 写*，而不只是单次工具调用。

**容器式约束。** 子 agent 带着一个编辑/写入守卫运行，拒绝写它自己的工作目录、共享
的 plans 目录和临时空间之外的地方。这是**纪律守卫而不是安全边界** —— 子 agent 有
shell 权限，而 shell 命令不受工具级钩子约束。它存在是为了拦住事故，知道它仅止于此
是值得的。

## 为什么要这样分层

每一层都在兜上一层兜不住的东西：

| 层 | 兜住 | 看不见 |
|---|---|---|
| 依赖图 | 声明的顺序约束 | 完全不看文件 |
| 冲突图 | 声明的文件重叠 | 未声明的重叠 |
| 锁 + 槽位 | 未声明的重叠、成本 | （自身范围内无盲区）|

依赖图是**前向计划**，槽位约束的是**成本**，而锁是**计划落空时**真正兜底的那一层。
只有图的设计会很快但偶尔出错；只有锁的设计会正确但不必要地串行。

## 重试与失败处理

失败的任务带着错误上下文重试，有上限。同一个任务反复失败会触发**子任务拆分**，而
不是再来一次一模一样的尝试；一个循环检测器会停下"一直以同样方式失败"的任务，而不
让它把整个预算吃光。

每个成功的任务都是一个 git 检查点（`[task-{id}]`），所以任意一个已完成任务处的
树状态都是可恢复的。

## 完成由两个信号共同判定

任务只有在**agent 自己的报告与它声明的 `test_command` 退出码一致**时才算完成。
任何一个单独都不够 —— 一份写得很漂亮但命令返回非零的总结不算完成；一条退出码为零
但**命令本身就选错了**的也是。

这也解释了为什么空 diff 是**警告**而不是失败：交付物是"一个结论"而不是"一处改动"
的审计类任务是合法的，而一个只问"文件变了没有"的门禁会把它们永远重试下去。见
[设计说明](../development/design-notes.md)。

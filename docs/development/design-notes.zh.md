# 设计说明

一些承重、但容易被误当成附带管线的决定。每一条都曾经是某次真实故障的成因 —— 这就是
它被写下来的原因。

## 两个独立的完成信号

任务只有在**agent 自己的报告与它声明的 `test_command` 退出码一致**时才算完成。
任何一个单独都不够；交叉验证取多数判决。

诱惑在于相信报告，因为它读起来顺、而且 agent 是唯一知道它想干什么的东西。反例正是
这条规则存在的全部理由：一份写得很漂亮的总结配一条返回非零的命令，不算完成；一条
退出码为零、但**命令本身就选错了**的，也不算。两个信号单独都不充分，因为它们**以
不同方式出错**。

## 空 diff 是警告，不是失败

早期有一道门禁会把任何没产生 diff 的任务硬判失败。那对整个一类合法工作是错的：交付
物是一个**结论**的审计类任务 —— 一个行号、一次 import 形状的验证、一份性能基线 ——
而不是一处改动。

失败模式很具体：这类任务被反复重试，直到计划彻底搁浅。现在它们会被识别出来（声明
`verification_only`，或按关键词判定），并交给**二次审计**比对规格的验收标准与提交的
答案，而不是依赖一次代码改动本会带来的运行时证据。

配套的另一半：非审计任务出现空 diff 是一条**警告**，操作者可以 grep 到它，而不是
静默通过。移除硬失败不等于移除信号。

## 到处都是有界的循环

这个系统里每一个重试循环都有上限，而每个上限都有一条比上限本身更有意思的提前退出：

- **验证轮次**在连续两轮以**完全相同**的验证点集合失败时提前停下 —— 修复没起作用，
  继续下去只是烧预算走到同一个地方。
- **任务重试**在反复失败后拆分子任务，而不是重复一次一模一样的尝试；循环检测器会
  停下"一直以同样方式失败"的任务。
- **子进程超时**杀掉整个进程组，而不只是直接子进程。命令经过 shell 运行时，
  `subprocess.run(..., timeout=N)` 做不到这一点：直接子进程是那个 shell，真正干活
  的东西活得比它久。

一个没有提前退出的循环不是"更彻底"，是一个没有主人的预算。

## `running` 是一个声明，不是证据

状态字段是由某个可能已经死掉的线程写下的。字段写着 `running`，意思是"最后一个写入
者这么说" —— 而当你真的出事时，这正是你所处的状态。

所以系统会拿这个声明去和文件系统对质：最新验证日志、执行结果文件、轮次报告的修改
时间。一个远超任何单步该花的时间都没有产出任何东西的进程，会被报成**卡住**，而不是
继续显得健康。同样的推理也适用于 `/health`（进程还在服务 HTTP 吗？）与
`/health/data`（它真的能读自己的库吗？）—— 一个服务完全可以对前者完全健康、对后者
已经死了。

## 状态 / 原因的契约

有几个停止条件是按**状态值**识别的，不是按 reason 字符串。这是刻意的：reason 字符串
是散文，它们会被改名，而比较它们的守卫会在有人改进措辞的那天静默失效。这件事真的
发生过 —— 改名之后收敛判据不再匹配，在那个版本发布期间一直是坏的，每一轮都烧完了
整个预算。

当一个条件需要被机器识别时，给它一个属于契约、并被测试钉住的值。

## 运行态只有一个目录

状态库、它的 WAL 兄弟、boot 计数器、关闭备份，一起放在一个 gitignored 目录下。它们是
一个整体，理由不是整洁：boot 计数器和备份目录的路径是从数据库的父目录推导出来的，
所以一次局部搬迁会造出"一个进程读它、另一个进程写它"的局面。

这类 bug 的一般形式是**从 `__file__` 多处重新推导同一个路径**。状态库路径曾经被推导过
九次，其中两处已经漂移过 —— 每一处**在写下的当天都是对的**。它现在只声明一次，并由
一道静态门禁守住。见[配置](../operations/configuration.md)。

## 读一个自己不拥有的文件

macOS keychain 门禁要判断 CI 车道是否以严格档运行整链路 E2E，做法是从那个 E2E 文件里
**读出**两个模块级常量 —— 开关的名字，以及它接受为"开"的值 —— 而不是自己留一份副本。
这个取舍是对的：E2E 文件才是"这个开关是什么意思"的定义处；留副本的门禁会在文件其实读
的是别的东西时，报出"车道处于严格档"。

代价是这道门禁有一个自己不掌控的输入，而这个输入的形状值得写下来。它解析的文件是从
**门禁自己所在的位置** 找到的 —— `Path(__file__).resolve().parents[3]` 再加一段固定后缀
—— 不是从工作目录，也不是从绝对路径。所以它读到的，就是与被收集到的门禁模块**同一棵树
里**的那个 E2E 文件。在 CI 里这意味着运行门禁那个 job 的 checkout，而真正收集 E2E 的
车道在另一个 runner 上 checkout 同一个 commit：同一路径、同一 commit、两个工作区。因此
一道绿灯的含义是"该 commit 上的那个文件如何"，而不是两个 job 的 checkout 之间的逐字节
比对。

既然要问，就值得把各种失败形态分清楚 —— 区别正在于此：

- **常量被改名或被删掉。** 一条干净的 `AssertionError`，点名文件与常量。门禁在干它该干
  的事。
- **常量在，但静态读不出来** —— 写成了一个表达式，而不是字面量或集合包装。同样是干净的
  `AssertionError`，由取值的那一层抛出，而不是找常量的那一层。
- **文件根本解析不了。** 标准库的 `SyntaxError` 直接逃了出来。报告里会点名 E2E 文件和
  出错的那一行，但栈顶那一帧是标准库里的解析器，而整条信息里没有任何地方说明**是哪道
  门禁**在读这个文件、它要的是**哪个常量**。一个没碰过 E2E 文件的读者，看到的是一个
  "他以为没有任何东西会去解析"的文件里的语法错误。门禁确实把路径作为 filename 传给了
  `ast.parse`，所以名字是对的 —— 但把这个异常渲染出来，只剩一个基名和一个行号，读者
  拿到的就只有这些。
- **文件没了。** 读文件时抛 `FileNotFoundError`，而不是门禁为它准备的那条存在性断言：
  有三道测试读这个文件，只有一道先检查它在不在。

一般形式就是上面那句：**一个输入不是自己写的读者，它的失败信息必须点名这个读者，而不只是
点名输入。** 干净的两种做到了；逃出去的两种没有 —— 而这两种逃逸，第一眼都像是门禁自身
逻辑的缺陷，而不是它读到了被破坏的输入。

## 契约可以由"一旦被破坏就失效的那个文件"来钉住

上面那些门禁用交叉引用来验证开关的**名字** —— 只改一边会变红；它们也通过"工作流设的
那个值是否**属于** E2E 文件声明的集合"来验证它。但它们并不钉住这个被接受的集合本身。
只改一边会被抓到；两边一起改 —— 无论是整体改名，还是把集合放宽到接受一个松散的写法
—— 仍然是绿的。

被接受的值在别处有钉：E2E 文件自己的真值表逐格断言了每种写法必须得出什么结论。所以这
个保证是存在的，只不过它待在同一个文件里 —— 而那正是"文件被破坏"会一起打掉的地方。
门禁的保证与取值的保证按构造共用同一个单点失效来源；这是这个设计的代价，不是它的缺陷
—— 但值得写下来，免得有人把那句交叉引用读得比它实际更重。

## 注释用来解释，不用来叙事

注释可以说代码做什么、为什么。它不可以引用某个人、点名一个兄弟仓、或者叙述某台机器
上发生过什么 —— 最后这条读起来像证据，而它恰恰是读者**唯一无法核对**的那类陈述。

失败史改由测试来承载，那是对的地方：一道门禁的 docstring，读它的正好是那个即将改动
它所保护之行为的人。

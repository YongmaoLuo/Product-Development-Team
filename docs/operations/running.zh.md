# 运行它

## 它是一个本机工具

有三条性质决定了它该怎么被运行，它们不是你可以绕过去的配置默认值：

1. **它会以你的身份、在你的机器上**写文件、起子进程、跑命令。它不是为共享、多用户
   或公网托管设计的，内部也没有任何东西把一个用户的工作和另一个用户的分开。
2. **REST API 是这个进程的管理面** —— 启动 / 停止 / 检视一次运行、读每个阶段产出的
   产物、驱动工作流。它的用途就是这个：从本地脚本或内置 UI 驱动**你自己这个实例**。
   它不是拿来交给别人的客户端调用的服务。
3. **API 没有认证。** 没有账户、没有登录、没有用户隔离。下面的 request guard 判断的
   是"调用方是不是**本实例自己的客户端**"；它不是认证，也不让这个端口变得可以对外
   暴露。

## Request guard

回环地址对**浏览器**来说不是安全边界。你访问的任何页面都能在你浏览器里向
`127.0.0.1:<端口>` 发请求，而服务端无法把它们和自己的 UI 区分开 —— 两者都从
127.0.0.1 来。

所以每个 `/api/*` 请求必须带：

```
X-PDT-Request: 1
```

这个值不是机密，**也不打算是**。请把这个头读作"**我不是一个外来网页**"的证明，
而不是密码：

- 带自定义头的**跨源**请求不再是 CORS 的"简单请求"，浏览器必须先发预检。本服务不
  回应任何预检（它根本没有安装 CORS 中间件），所以外来页面**根本发不出这一发**。
  知道这个值也没用 —— 拒绝发送的是浏览器，不是服务端拒绝接收。
- `Origin` 不是本机时会被拒，这对应的是绕过上面那条的跨源页面。
- `Host` 不是本机时会被拒，这对应的是 **DNS rebinding** —— 攻击者的域名解析到
  127.0.0.1，浏览器认为请求是同源的，于是前面两条都不会触发。

有两样是**刻意留开的**，两样都写在这里，而不是留给别人日后踩到：

- **静态资源。** 浏览器**导航**无法附带请求头，要求带就等于 UI 打不开。它们本来就是
  本仓已有内容的只读副本。
- **`/health` 和 `/health/data`** 不在 `/api/` 前缀下，因此同样不受 guard 覆盖。
  它们回答的是"活着吗"和"服务能不能读自己的状态库"，后者在失败时还会报出异常类型。

### UI 的 fetch 契约

内置 UI 会替你带上这个头 —— 但只通过它的两个包装函数。**其他 JS 模块里的裸
`fetch(...)` 会拿到 `403 Forbidden`**，因为浏览器不会自己附带 `X-PDT-Request: 1`。

| 包装 | 谁在用 |
|---|---|
| `frontend/api.js` 里的 `apiRequest(path, options)` | 验证相关的视图 |
| `frontend/app.js` 里的 `api(path, options)` | 内置 UI 的其余部分 |

两者都会带上请求头、解析 JSON，并在非 2xx 时抛出 `Error`，其 `.detail` 携带服务端的
`detail` 字段。

其他写法 —— 在新视图里手敲的 `fetch(...)`、一次性的 `XMLHttpRequest`、被第三方页面
注入的 script 标签 —— 都过不了预检，永远到不了服务端。这条规则同样被钉在源码层：
`backend/tests/static_gates/test_frontend_uses_api_wrapper.py` 审计 `frontend/` 下
每一个 `.js` 文件，拒绝任何追溯不到这两个包装的裸 `fetch(`。

直接驱动 API 的脚本需要显式带上请求头：

```bash
curl -H 'X-PDT-Request: 1' http://localhost:8000/api/plans
```

## 回环之外

如果你确实需要（容器、你自己控制的 VM），显式设置 `PDT_HOST`、把你用来访问它的
非回环主机名加进 `PDT_ALLOWED_HOSTS`，并在它前面放上你自己的认证：

```bash
PDT_HOST=0.0.0.0 PDT_ALLOWED_HOSTS=pdt.internal python -m backend.server
# 仅在自有认证代理之后、在你信任的网络里
```

除非有明确理由并且清楚那个网段上还有谁，否则不要设 `PDT_HOST`。

## 观察一次运行

| 调用 | 回答 |
|---|---|
| `GET /api/plan/{id}/summary` | 一句话说明计划当前状态的那个调用 |
| `GET /api/execution/{id}/progress` | 任务计数、当前任务、下一个任务 |
| `GET /api/execution/{id}/status` | 进程状态加最近的日志行 |
| `GET /api/execution/{id}/logs?level=WARNING` | 过滤后的执行日志 |
| `GET /api/execution/{id}/diagnose` | 对卡住的运行给出诊断与建议 |
| `GET /api/execution/{id}/files` | 实际落到磁盘上的东西 |
| `GET /api/verification/{id}/status` | 轮次、状态、停止原因、结果 |

执行日志以 JSON-lines 持久化在 `plans/{plan_id}/execution.log`，所以它们能跨服务重启
存活 —— 内存里的日志视图不能。`progress` 跨重启依然可靠是同一个道理，但它读的是
**两个**磁盘来源而不是一个：来自 `tasks.json` 的**静态任务图**，以及来自状态数据库
（`.pdt/state.db`）的**每任务运行态** —— 状态、尝试次数、commit sha、结束时间。
`tasks.json` 只存静态数据，所以重启既不会丢一个任务的进度，也不会留下半写状态。

!!! tip "`running` 是一个声明，不是证据"
    `verification_status: "running"` 反映的是一个内存字段。一轮验证如果长时间没有任何
    日志输出，它卡住的可能性远大于它慢。在相信状态字段之前，先看
    `plans/{plan_id}/logs/` 下最新文件的修改时间 —— 那正是 watchdog 心跳替你做的事，
    它会把一个不再上报的线程标出来，而不是永远等下去。

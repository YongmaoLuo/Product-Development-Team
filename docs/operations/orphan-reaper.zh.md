# 孤儿进程回收器

PDT 会拉起一批进程 —— 一个后端、一个 fixture、一个 agent、一个辅助程序 —— 其中大多数
本应随启动它们的东西一起消失。有些不会。当父进程被强杀（swap 风暴、jetsam、
`kill -9`），子进程会被重新挂到 pid 1 下面，继续占着它的内存，而机器上已经没有任何
东西知道它属于 PDT。

**孤儿进程回收器**（orphan reaper）补的就是这个缺口。它扫描机器，判定哪些进程确实
成了孤儿，再把该回收的回收掉：`SIGTERM`，一段宽限期，然后 `SIGKILL`。

它的设计刻意保守。只有 PDT 自己标记过的进程才可能是候选，而每一种「说不准」都一律
倒向「不去动它」。本页是运维契约：回收器认得什么、怎么配置、审计记录落在哪里，以及
它拒绝动手的四种条件。

## 进程如何被认出来是「我们的」

回收器不靠工作目录、也不靠命令行长什么样来猜：PDT 是开源的、跑在别人机器上，这两个
信号在那里都靠不住。所有 PDT 拉起的进程都带着一个**PDT 自己写进去的标记**，并且被后代
继承：

| 标记 | 含义 |
|---|---|
| `PDT_SPAWN_OWNER_PID` | 拉起它的那个进程的 pid |
| `PDT_SPAWN_OWNER_START` | 该 owner 的启动时间 —— 它用来识破 pid 复用 |
| `PDT_SPAWN_KIND` | 它是什么：`service`、`fixture`、`subprocess`、`agent` 或 `reaper` |

让这套方案成立的，是两个性质：

* **owner 在每一层 spawn 时都会重新打标**，而不是只在最顶上打一次。进程的 owner 是真正
  启动它的那个进程，所以父进程已死的孙进程即使顶层后端还在跑，也是孤儿。
* **owner 的启动时间和 pid 一起传下去。** pid 本身不是身份 —— 内核会回收 pid —— 所以
  标记里记下的是 owner *何时*启动的。pid 还活着、但启动时间与记录不符的，是一个碰巧
  同号的另一个进程，不能碰。

## 配置

一切都是环境变量，而且每个默认值都是安全的那一个 —— 一个什么都不配置的部署，最多只能
回收 PDT 自己标记过的进程。

| 变量 | 默认值 | 含义 |
|---|---|---|
| `PDT_ORPHAN_REAPER` | `1` | `0` 完全关闭 |
| `PDT_ORPHAN_REAPER_INTERVAL` | `30` | 两次扫描之间的秒数 |
| `PDT_ORPHAN_REAPER_PROTECT_PORTS` | `(none)` | 额外保护端口，逗号分隔；是**追加**到默认值上，绝不替换默认值 |
| `PDT_ORPHAN_REAPER_GRACE` | `5` | SIGTERM 到 SIGKILL 之间的宽限秒数 |
| `PDT_ORPHAN_REAPER_IDLE_EXIT` | `1800` | 守护进程空闲这么多秒后退出；`0` 关闭自我退出 |

默认保护端口是 `8000`、`8002`、`3000`、`3001` 和 `8651` —— PDT 自己的常驻服务（后端、
supervisor、两个前端，还有一个服务）。占着其中之一的进程，很可能是有人在用的服务，
所以默认受保护。

值写错从不抛异常：它退回默认值，因为一个因为一个错别字就拒绝启动的回收器，会把它本来
要回收的内存留在那里。`PDT_ORPHAN_REAPER=0` 时，一轮扫描只会打印 `disabled`，什么也
不做。

## 运行方式

回收器只依赖标准库，所以它能独立运行：

```bash
python -m backend.orphan_reaper --once
```

| 参数 | 作用 |
|---|---|
| `--once` | 跑一轮：扫描、回收、把事件记下来、每个判定打印一行，然后退出 |
| `--daemon` | 每隔 `interval` 秒跑同样的一轮，直到它被停掉（`SIGTERM`/`SIGINT`），或者机器已经安静了 `idle_exit` 秒 |
| `--dry-run` | 只判定不发信号：每个判定都会走到并被记录，一个信号都不发 |
| `--interval` | 覆盖扫描间隔，单位秒 |
| `--plans-root` | 覆盖 plan 产物的根目录（默认 `$PDT_PLANS_DIR`，否则是 `<repo>/plans`） |

不带 `--once` 也不带 `--daemon` 时，回收器打印出它解析出来的配置就退出，什么都不动。

守护进程是**单例**：它运行期间持有回收器的锁，第二个实例会立刻让位 —— 两个回收器会在
同一批候选上互相抢，并且把同一段宽限期施加两次。

**一轮扫描打印什么。** 每个判定一行 —— `pid decision reason`，判定自带标记类型时还会
带上类型：

```
4711 kill orphan service
4712 skip unmarked
```

**审计记录落在哪里。** 每一轮扫描都往下面这个文件追加一行一个判定的 JSON —— 杀掉的和
跳过的都记：

```
<plans_root>/.orphan-reaper/kill_events.jsonl
```

一条记录长这样：

```json
{"ts": "2026-10-27T10:00:00", "pid": 4711, "ppid": 1, "pgid": 4711, "argv": "python -m backend.server", "rss": 213000, "owner_pid": 999, "owner_start": "17", "reason": "orphan", "signal": "TERM"}
```

`signal` 说明发出去的是什么 —— `TERM`、`KILL`，或者 dry run 时的 `none` —— 对每一个
不是杀的判定它是空的。日志只追加、不重写：一个每三十秒跑一次的回收器，不能弄丢三十秒
前它做过什么的记录。写失败只是一条警告，别无其它：回收器的存在是为了把内存还回去，
磁盘写满不该拦住它干这件事。

## 判定阶梯

每个候选都按固定顺序走一遍判定阶梯。下面这六级，是把「是我们的、而且确实成了孤儿」
和其余一切分开的地方；本页没有列出的那几级 —— `other_uid`（进程属于另一个用户）、
`env_unreadable`、`owner_unknown` 和 `ports_unknown` —— 只可能跳过，详见本页最后一节。

任何一级都不能把一次跳过变成一次杀：只有先通过前面所有级，才能走到最后一级，而最后
一级是唯一可能发出信号的一级。

### 1. 无 PDT 标记

一个完全没有 `PDT_SPAWN_*` 标记的进程不是我们的，所以它永远不是候选。日志里记下的
理由是 `unmarked`。用户手动起的东西 —— 他自己跑的 pytest、他自己的编辑器、一个无关的
服务 —— 对回收器而言永远不可见。

### 2. owner 存活

owner 还活着的进程永远不是候选，哪怕其它标记全都对。理由是 `owner_alive`；owner 活着
但两个启动时间没能比上时，理由是 `owner_alive_unverified` —— 那也仍然是跳过。

### 3. PID 复用

pid 不是身份：内核会回收它们。当 owner 的 pid 还活着、但它的启动时间与记录的不一致时，
那是一个碰巧同号的另一个进程，候选进程不予处理。理由是 `pid_reused`。

### 4. 保护端口

占着保护端口的进程永远不是候选。理由是 `protected_port`。保护集合是默认端口加上
`PDT_ORPHAN_REAPER_PROTECT_PORTS` 追加的内容 —— 只加不减。

### 5. reaper 自身

回收器从不给另一个回收器发信号，也绝不给 pid 1 或自己发信号。理由是 `self_reaper`
（或 `self`）。

### 6. owner 已死 → 回收

只有带着标记、owner 确定已经不在、不占任何保护端口、而且自己不是回收器的进程，才会
走到这一级。理由是 `orphan`，而它是唯一可能导致信号的理由：`SIGTERM`，然后宽限期，
然后 `SIGKILL`。

## 不确定性一律倒向「不杀」

上面那几级里有两级是**降级**而不是判断：一个读不到的环境是**未知**，不是空；一张读不到
的端口表也是**未知**，不是空。「说不准」不是任何证据的证明，把它当成证据，正是一个无关
进程被送上 kill 名单的方式。owner 根本没法检查（`owner_unknown`）、端口表根本读不出来
（`ports_unknown`）时也是一样。

这就是 **fail-closed** 规则：回收器分不清的时候，就不去动那个进程。读不出来的标记、
定不下来的启动时间、查不了的 pid —— 每一个都意味着跳过，绝不意味着杀。

**在 macOS 上读一个读不出来的环境。** macOS 没有 `/proc`，而 `sysctl kern.procargs2`
在这个平台上也不暴露环境，所以环境是通过 `ps -E` 读的。Apple 自己的二进制受 SIP 保护：
`ps -E` 能看到它们的命令行，看不到任何环境。

一次读取产出了输出、却一个 `k=v` 段都没有，因此意味着*读不出来* —— 不是空。这样的进程
会被记成理由 `env_unreadable` 并被跳过，绝不会被杀。**这是设计如此，不是故障**：回收器
无法判断一个 Apple 平台二进制是否带着标记，而「无法判断」就倒向不去动它。在日志里看到
`env_unreadable`，说明边界守住了，而不是说哪里坏了。
